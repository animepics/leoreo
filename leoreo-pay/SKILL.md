# Leoreo Pay — 한국 결제시스템 & 수익모델

한국에서 돈을 받는 개발을 할 때 로드하는 스킬이다. 순서가 중요하다: **수익모델 → 가격 → 결제 인프라 → 구현 → 규제**. 결제 코드를 먼저 짜고 수익모델을 나중에 정하면 갈아엎게 된다.

> 수수료율·정책·법령은 변동이 잦다. 부록의 수치는 2025~2026년 조사 기준이며, 계약/구현 직전에 PG 공식 문서와 견적으로 반드시 재확인한다.

## 1단계 — 수익모델 선택 (무엇으로 돈을 받나)

사업유형별 기본값 (상세: `references/revenue-models.md`):

| 사업 유형 | 기본 모델 | 보조 |
|---|---|---|
| B2C 앱 | Freemium + 구독 | 광고, 인앱 단건 |
| B2B SaaS | 구독(Tiered) + 종량 하이브리드 | 순수 좌석제는 축소 추세(이탈률 2.3배) |
| 마켓플레이스 | Commission/take rate | 프리미엄 리스팅, 광고 |
| 콘텐츠 | 구독 (국내 심리 표준가 9,900원대) | freemium+광고 |
| API/개발자도구 | 종량제 (미터링 인프라 선투자 필요) | 구독 플로어 + 크레딧 |
| AI 제품 | 하이브리드(구독 플로어 + usage) | 추론 원가가 마진을 깎으므로 순수 정액은 위험 |

결정 규칙:
- 사용자당 월 AI/변동 원가가 미미하면 번들(구독가 포함), 크면 크레딧/오버리지 분리.
- 종량제·수수료 모델은 결제 구현 난이도가 가장 높다(미터링, 양방향 정산, 에스크로). 구현 비용도 모델 선택 변수다.
- 수익모델 전환(단건→구독)은 grandfathering + 국내법상 유료전환 사전동의(14~30일) 필수.

## 2단계 — 가격 설계 (얼마 받나)

- 순서: cost-plus로 바닥 → 경쟁가로 범위 → **value-based로 최종가** (제공 가치의 10~20%).
- 티어는 Good-Better-Best 3단. 최고가 티어는 앵커. 국내 B2C는 9,900원대 charm pricing이 표준.
- 연간 플랜 = 월간 대비 15~20% 할인("2개월 무료" 프레이밍이 전환율 더 높음).
- Trial: 14일이 최빈이지만 **전환율은 7일이 최고(24%)**. 카드 사전등록 시 전환율 ~5배.
- Freemium 전환율 베이스라인 2~5%(셀프서브).
- Take rate: 상품형 5~15%, 서비스형 15~30%. 국내 배민 2~7.8% 차등제 참고. 플랫폼 부가가치(신뢰/에스크로/발견성)가 수수료를 정당화 못 하면 우회(디스인터미디에이션) 발생.

## 3단계 — 결제 인프라 선택 (한국)

상세: `references/korea-pg.md`

- **기본 권장**: 시드~시리즈A는 포트원류 멀티 PG 게이트웨이로 시작(연동 1회, PG 교체 자유, 장애 라우팅). 거래량 커지면 단일 PG 직연동으로 수수료 최적화.
- **직연동 시**: DX 최우선 토스페이먼츠 / 해외카드 NHN KCP / 초기비용 최소 나이스페이먼츠 / 대형 커머스 KG이니시스.
- **구독이면**: 빌링키 방식 필수. 국내 간편결제(카카오/네이버/토스페이)는 대부분 빌링 미지원 — 카드 중심으로 UX 설계. 카드 만료 시 빌링키 갱신 개념이 없어 재발급 플로우를 직접 구현해야 한다.
- **앱이면**: 순수 디지털 콘텐츠는 인앱결제 강제 대상. 제3자결제도 수수료 26%라 실익 작음. 실물/오프라인 연계만 PG 웹결제 가능.
- **해외 판매면**: 한국 사업자는 Stripe 직접 개설 불가. MRR 작을 때는 Paddle/Lemon Squeezy류 MoR(실효 ~7%, 세금 대행), 커지면 해외법인+Stripe 검토.

## 4단계 — 구현 (엔지니어링 불변식)

상세 및 전체 체크리스트: `references/payment-engineering.md`. 아래는 절대 규칙:

1. **Order와 Payment 분리** (1:N). 상태 전이는 단방향 + 현재 상태 기준 가드.
2. **금액 위변조 검증**: 클라이언트가 보낸 금액을 절대 신뢰하지 않는다. 승인 직전 서버 저장 금액과 대조, 불일치 시 승인 거부.
3. **멱등성**: 모든 결제/취소 API에 idempotency key. 멱등 기록과 비즈니스 처리는 같은 DB 트랜잭션.
4. **웹훅**: raw body로 서명 검증, event id에 unique 제약으로 중복 차단, 순서 뒤바뀜은 상태 머신 가드로 방어, 유실 대비 폴링/일 배치 대사 백업. successUrl 리다이렉트만으로 결제 완료 확정 금지.
5. **금액은 정수(int/bigint)**. float 금지. 대사는 payout 총액이 아니라 거래 단위로.
6. **환불**: 결제수단별 분기(가상계좌 부분취소 불가 등), 누적 취소액 서버 검증, 취소에도 멱등키.
7. **dunning**: soft/hard decline 구분. soft는 시차 재시도(1·3·7일), hard는 결제수단 변경 유도. 자체 브랜드 알림 발송(실패 결제 최대 40% 회수).
8. **보안**: 카드 원본정보 자체 저장 금지(빌링키 암호화 저장), 시크릿 키 서버 전용, 로그 마스킹.

## 5단계 — 규제 체크 (한국, 놓치면 벌금)

- **청약철회 7일 / 환불 3영업일** (전자상거래법) — 환불 워크플로우에 기한 자동 트리거.
- **구독 자동갱신**: 갱신 사전 고지, 요금 인상 30일 전(유료전환 14일 전) 동의, 옵트아웃 UI — 3종 세트 필수 구현.
- **해지 플로우**: 리텐션 오퍼는 1~2단계까지만, 해지 버튼은 오퍼와 동시 노출, 가입≒해지 단계 수 대칭. 다크패턴은 규제 리스크(Amazon Prime $2.5B 합의).
- **현금영수증**: 의무발행업종이면 10만원 이상 현금거래 무조건 발급. B2B는 세금계산서 발행 연동 고려.
- **전자금융거래법 개정(2026.12.17 시행)**: PG 정산자금 외부 신탁/예치 의무화 — PG 선정 시 준수 여부 확인. 자체 정산/중개 모델을 설계한다면 PG업 등록 요건 법무 검토 필수.

## 출력 규칙

- 설계 요청이면: 1→5단계 순서로 결정사항을 채우고, 미정 항목은 사용자에게 묻거나 명시적 가정으로 표기한다.
- 구현 요청이면: 4단계 불변식을 코드에 강제하고, `references/payment-engineering.md`의 시나리오 테스트 체크리스트(금액 조작, 중복 웹훅, 순서 뒤바뀜 등)를 테스트에 반영한다.
- 수치(수수료·벤치마크·법령)를 인용할 때는 "조사 시점 기준, 재확인 필요" 단서를 붙인다.
