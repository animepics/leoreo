# Leoreo Pay — 한국 결제시스템

한국에서 돈을 받는 기능을 설계하고 구현할 때 로드하는 스킬입니다. 수익모델과 가격이 아직 정해지지 않았다면 `leoreo-model` 스킬을 먼저 적용합니다. 모델이 정해져야 아래 인프라 요구사항이 결정되기 때문입니다.

| 수익모델 | 따라오는 결제 인프라 |
|---|---|
| 구독 | 빌링키, dunning(실패 재시도), 자동갱신 고지 |
| 종량제/크레딧 | 미터링(멱등 집계), 잔액 관리, 오버리지 청구 |
| 중개/마켓플레이스 | 에스크로, 양방향 분리 정산, PG업 등록 검토 |
| 단건 판매 | 기본 결제 플로우 + 환불 워크플로우 |
| 해외 판매 | MoR(Paddle 등) 또는 해외법인+Stripe |

> 수수료율·정책·법령은 자주 바뀝니다. 아래와 부록의 수치는 2025~2026년 조사 기준이니, 계약이나 구현 직전에 PG 공식 문서와 견적으로 다시 확인합니다.

## 1단계 — 결제 인프라 선택

상세 비교는 `references/korea-pg.md`에 있습니다.

- 시드~시리즈A 단계라면 포트원 같은 멀티 PG 게이트웨이로 시작하는 편이 좋습니다. 연동을 한 번만 하면 되고, PG 교체가 자유롭고, 특정 PG 장애 때 트래픽을 돌릴 수 있습니다. 거래량이 커지면 단일 PG 직연동으로 수수료를 줄이는 걸 검토합니다.
- 직연동을 한다면: 개발 경험은 토스페이먼츠, 해외카드는 NHN KCP, 초기비용은 나이스페이먼츠, 대형 커머스는 KG이니시스가 각각 강합니다.
- 구독 서비스라면 빌링키 방식이 필수입니다. 카카오페이·네이버페이·토스페이 같은 간편결제는 대부분 정기결제를 지원하지 않아서, 구독 UX는 카드 중심으로 설계합니다. 카드가 만료되면 빌링키를 새로 발급받는 플로우도 직접 만들어야 합니다.
- 앱이라면: 순수 디지털 콘텐츠는 인앱결제 대상입니다. 제3자결제도 수수료가 26%라 실익이 작고, 실물·오프라인 연계 서비스만 PG 웹결제를 쓸 수 있습니다.
- 해외에 판다면: 한국 사업자는 Stripe 계정을 직접 만들 수 없습니다. 규모가 작을 때는 Paddle이나 Lemon Squeezy 같은 MoR(실효 수수료 약 7%, 세금 신고 대행)로 시작하고, 커지면 해외법인+Stripe를 검토합니다.

## 2단계 — 구현 불변식

전체 내용과 체크리스트는 `references/payment-engineering.md`에 있습니다. 아래 여덟 가지는 예외 없이 지킵니다.

1. **Order와 Payment를 분리합니다** (1:N). 상태 전이는 단방향으로 하고, 현재 상태 기준으로 허용된 전이인지 가드를 겁니다.
2. **금액 위변조를 검증합니다.** 클라이언트가 보낸 금액은 조작될 수 있으니, 승인 직전에 서버에 저장해 둔 금액과 대조하고 다르면 승인하지 않습니다.
3. **멱등성을 보장합니다.** 모든 결제·취소 API에 idempotency key를 붙이고, 멱등 기록과 비즈니스 처리를 같은 DB 트랜잭션으로 묶습니다.
4. **웹훅은 raw body로 서명을 검증하고**, event id에 unique 제약을 걸어 중복을 막고, 순서가 뒤바뀐 이벤트는 상태 머신 가드로 걸러냅니다. 유실에 대비해 폴링이나 일 배치 대사를 백업으로 둡니다. successUrl 리다이렉트만 믿고 결제 완료를 확정하면 안 됩니다.
5. **금액은 정수(int/bigint)로 다룹니다.** float는 반올림 오차가 쌓입니다. 대사는 정산 총액이 아니라 거래 단위로 맞춥니다.
6. **환불은 결제수단별로 분기합니다.** 가상계좌는 부분취소가 안 되고, 계좌이체는 자동환불이 없습니다. 누적 취소액이 원 결제액을 넘지 않는지 서버에서 검증하고, 취소 API에도 멱등키를 붙입니다.
7. **결제 실패는 soft/hard decline을 구분합니다.** 일시적 실패는 1·3·7일 시차 재시도, 구조적 실패는 결제수단 변경 유도로 갑니다. 알림은 자사 브랜드로 보내야 회수율이 높습니다(실패 결제의 최대 40% 회수).
8. **카드 원본정보는 저장하지 않습니다.** 빌링키를 암호화해 보관하고, 시크릿 키는 서버 전용으로 두고, 로그에서 카드번호·개인정보를 마스킹합니다.

## 3단계 — 한국 규제 체크

놓치면 과태료나 환불 분쟁으로 돌아옵니다.

- **청약철회 7일, 환불 3영업일** (전자상거래법). 환불 워크플로우에 기한을 자동으로 걸어둡니다.
- **구독 자동갱신 3종 세트**: 갱신 사전 고지, 요금 인상 30일 전(유료 전환 14일 전) 동의, 동의 취소(옵트아웃) UI.
- **해지 플로우**: 리텐션 오퍼는 1~2단계까지만 두고, 해지 버튼은 오퍼와 같은 화면에 노출하고, 해지 단계 수를 가입과 비슷하게 맞춥니다. 다크패턴은 규제 리스크가 큽니다(Amazon Prime이 FTC와 25억 달러에 합의한 사례가 있습니다).
- **현금영수증**: 의무발행업종이면 10만원 이상 현금거래에 요청이 없어도 발급해야 합니다. B2B라면 전자세금계산서 발행 연동을 함께 검토합니다.
- **전자금융거래법 개정(2026.12.17 시행)**: PG 정산자금 외부 신탁·예치가 의무화됩니다. PG를 고를 때 준수 여부가 정산 지연·도산 리스크의 지표가 됩니다. 자체 정산이나 중개 모델을 만든다면 PG업 등록 요건을 법무 검토합니다.

## 출력 규칙

- 사용자와 소통할 때는 되도록 쉬운 말을 씁니다. 멱등성·dunning 같은 용어가 필요하면 첫 등장에 괄호로 풀이를 붙입니다(예: 멱등성(같은 요청이 두 번 와도 한 번만 처리됨), dunning(결제 실패 시 재시도·안내)).
- 설계 요청이면 인프라 선택 → 구현 → 규제 순서로 결정사항을 채우고, 정해지지 않은 항목은 사용자에게 묻거나 가정을 밝힙니다.
- 구현 요청이면 2단계 불변식을 코드에 반영하고, `references/payment-engineering.md`의 시나리오 테스트 목록(금액 조작, 중복 웹훅, 순서 뒤바뀜 등)을 테스트에 넣습니다.
- 수수료·법령 수치를 인용할 때는 조사 시점 기준이라는 단서를 붙입니다.
