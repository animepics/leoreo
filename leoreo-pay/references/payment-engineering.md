# 결제 엔지니어링 부록 — 설계 불변식과 체크리스트

토스페이먼츠/Stripe 공식 문서와 업계 표준 패턴 기준. 실제 연동 직전에는 해당 PG의 최신 API 레퍼런스로 상태값·필드명을 재확인한다.

## 1. 결제 상태 머신

### 상태 모델 (토스페이먼츠 v2 기준)
`READY → IN_PROGRESS → DONE / ABORTED / EXPIRED`, 가상계좌는 `WAITING_FOR_DEPOSIT` 경유, 취소는 `CANCELED / PARTIAL_CANCELED` 분기. (Stripe PaymentIntent: `requires_payment_method → requires_confirmation → requires_action → processing → succeeded/canceled` — PaymentIntent 하나당 성공 charge 최대 1개가 불변식.)

### 규칙
- 상태 전이는 **단방향**. `DONE → IN_PROGRESS` 역행 불가. 취소는 별도 하위 상태.
- 웹훅/폴링으로 상태 갱신 시 **현재 저장 상태 기준으로 허용된 전이인지 가드** — 중복·순서 뒤바뀐 이벤트의 역행을 차단.
- **Order와 Payment 분리 (1:N)**: 인증과 승인이 비동기라 합치면 정합성이 깨진다. 분리하면 재시도 다건·환불 이력 추적·PG 교체가 깔끔해진다.

### 금액 위변조 검증 (필수 보안)
클라이언트가 보낸 금액은 개발자도구로 조작 가능 — 절대 신뢰 금지.
1. 결제 요청 **전에** orderId + 최종 금액을 서버에 저장
2. successUrl 콜백의 amount를 저장 금액과 대조
3. 불일치 시 승인 API 호출 없이 즉시 거부
4. 승인 호출 자체도 서버가 orderId로 조회한 금액 사용

## 2. 멱등성 (Idempotency)

- 필요 이유: 승인 API 타임아웃 시 서버는 성공했는데 클라이언트가 재시도 → **이중 승인**.
- 모든 POST(결제·취소)에 `Idempotency-Key` 헤더. 토스: 최대 300자, 15일 유효, 처리 중 재요청 409, 같은 키 다른 payload 422. Stripe: 첫 응답(성공/실패 모두)을 저장했다 그대로 반환.
- 이중 방어: idempotency key(UUID) + 비즈니스 키(orderId)에 DB unique 제약.
- **핵심 실패 모드**: 멱등 기록과 실제 비즈니스 처리(승인/포인트 지급)를 분리하면 "처리 후 기록 전 크래시 → 재시도가 이중 처리". **같은 DB 트랜잭션으로 묶어라.**

## 3. 웹훅

- **리다이렉트(successUrl)는 신뢰 불가**: 브라우저 종료/네트워크 단절이면 아예 안 온다(토스는 10분 내 승인 미호출 시 EXPIRED). 웹훅은 서버-서버라 클라이언트 상태와 무관 — 결제 완료 확정은 웹훅/승인 응답 기준.
- **서명 검증은 raw body로**: JSON 파싱 후 검증하면 원본 바이트가 손상돼 실패한다 (Express면 해당 라우트만 `express.raw()`). 토스는 `payload:transmission-time`을 HMAC-SHA256.
- **중복 수신(at-least-once)**: check-then-process는 레이스에 진다 — **event id에 DB unique 제약**을 걸고 두 번째 INSERT의 제약 위반을 "이미 처리됨"으로 해석.
- **순서 뒤바뀜**: refunded가 paid보다 먼저 올 수 있다. 타임스탬프/버전으로 stale 이벤트 스킵 + 상태 머신 가드. 핸들러는 검증+큐잉만 하고 상태 갱신은 단일 워커가 순차 처리.
- **유실 대비**: 웹훅은 100% 보장이 아니다 — 폴링 또는 일 배치 대사 백업 필수. 토스는 실패 시 최대 7회 재시도(지수 백오프, 총 ~3일 19시간), 수신 측은 **10초 내 2xx** 응답.

## 4. 대사(Reconciliation)와 정산

- Payout(정산 입금)은 순액(gross − 수수료 − 환불)이다 — 총액 비교가 아니라 **개별 거래(balance transaction) 단위 매칭**.
- 최소 월 1회, 실무는 **일 배치 대사** 권장. 불일치는 조정 내역과 함께 이력 문서화. (배민 정산팀 원칙: "1원의 오차도 안 된다".)
- **이중장부(double-entry)**: 결제 이벤트당 차변/대변 동시 기록 → 잔액이 자기검증돼 불일치 조기 탐지.
- **금액은 정수**: float 금지(반올림 오차 누적). 최소 통화 단위 정수(KRW는 원 단위 int/bigint). API 경계에서 표현(정수/문자열/소수)을 명시하고 변환은 경계에서 한 번만 — 금액 버그 최다 발생 지점.

## 5. 환불/취소

- 부분 취소는 `cancelAmount`류 파라미터로. **가상계좌는 부분취소 불가**, 카드 부분취소는 3~4영업일 — 결제수단별 분기 필수.
- 취소 이력은 다건 배열로 관리, **누적 취소액 ≤ 원 결제액**을 서버에서 검증.
- **취소 API에도 멱등키** — 관리자 더블클릭/재시도로 이중 환불 방지.
- 계좌이체는 자동환불 미지원 — 별도 환불 프로세스(계좌정보 수집) 설계.

## 6. 실패 처리와 Dunning

- 실패 분류 후 전략 분기:
  - **Soft decline**(일시 잔액부족, 카드사 오류, 타임아웃): 시차 재시도(1·3·7일 패턴). Stripe Smart Retries는 ML로 1~8주 내 최적 시점 선택.
  - **Hard decline**(정지/분실, 만료, 구조적 한도초과): 재시도 무의미 — 결제수단 변경 유도.
- 결제 실패의 ~25%가 involuntary churn(SaaS 전체 이탈의 20~40%). 재시도+알림 병행 시 실패 결제 최대 40% 회수, 회수된 구독은 평균 7개월 더 유지.
- dunning 알림은 **자사 브랜드 발신**이 PG 일반 템플릿보다 효과적.

## 7. 보안

- **카드 원본정보 자체 저장 금지** — 빌링키/토큰화로 PCI-DSS 범위를 PG에 이전. 빌링키도 암호화 저장.
- **시크릿 키는 서버 전용** — 클라이언트 번들/앱에 절대 포함 금지. 테스트/라이브 키 환경 분리.
- successUrl 파라미터를 그대로 신뢰하지 않기(1절), orderId unique 제약으로 이중 승인 차단, 결제 폼에 CSRF 토큰.
- 로그 마스킹: 카드번호(앞6/뒤4만), CVC, 시크릿 키, 개인정보 — 구조화 로깅 단계에서 필터 강제.

## 8. 테스트

- PG 샌드박스로 빌링키 발급→승인→취소 전 과정 검증. 테스트/라이브 키를 환경변수 레벨에서 분리.
- 웹훅 로컬 테스트: Stripe CLI `stripe listen --forward-to localhost:.../webhooks` 또는 ngrok 터널링.

### 시나리오 테스트 체크리스트
- [ ] 정상 승인
- [ ] 실패 케이스별(잔액부족/한도초과/정지카드)
- [ ] 승인 타임아웃 → 재시도 시 멱등키로 이중승인 차단 확인
- [ ] 웹훅 중복 수신 → 이중 처리 없음
- [ ] 웹훅 순서 뒤바뀜(취소가 승인보다 먼저) 처리
- [ ] 부분취소/전액취소/초과 취소 거부
- [ ] 클라이언트 금액 조작 → 서버 거부
- [ ] successUrl 유실(브라우저 강제종료) 후 웹훅/폴링 복구
- [ ] 가상계좌 입금 웹훅 처리
- [ ] 웹훅 서명 위조 → 거부

### 운영 전환 체크리스트
- [ ] 라이브 키 전환(시크릿 매니저, 하드코딩 금지)
- [ ] 웹훅 엔드포인트 공인 HTTPS + PG 대시보드 등록
- [ ] 웹훅 실패/재시도 모니터링 알림
- [ ] 일 배치 대사 스케줄러 가동

## 구현 전 종합 체크리스트

**상태**: Order/Payment 분리 · 단방향 전이+가드 · 승인 직전 금액 대조
**멱등성**: 모든 결제/취소에 멱등키 · 멱등 기록과 처리를 같은 트랜잭션
**웹훅**: raw body 서명 검증 · event id unique · 폴링/대사 백업 · 리다이렉트만으로 완료 확정 금지
**대사**: 정수 금액 · 거래 단위 매칭 · 이중장부
**환불**: 수단별 분기 · 누적 취소액 검증 · 취소 멱등키
**dunning**: soft/hard 구분 · 자사 브랜드 알림
**보안**: 카드정보 비보관 · 시크릿 서버 전용 · 로그 마스킹
**테스트**: 위 시나리오 전 항목 + 운영 전환 체크
